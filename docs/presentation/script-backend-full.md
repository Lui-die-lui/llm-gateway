# 발표문 · 누가 쓰고, 전체가 어떻게 돌아가는가 (백엔드 중심)

1~4번까지 말하는 속도로 약 5분 30초입니다. 5~8번은 질문이 나올 때 쓰는 참고 자료입니다. `[ ]` 안은 넘기는 슬라이드나 보여 줄 화면입니다. 숫자는 코드와 시험에서 직접 센 값입니다.

---

## 1. 시작: 문제 (40초)

직원들은 이미 ChatGPT와 Claude를 씁니다. 문제는 그때 무엇을 붙여넣느냐입니다. 고객 이름이 든 메일, 서버 주소, API 키, 아직 내놓지 않은 제품의 배합표까지 아무렇지 않게 들어갑니다. 한 번 나간 글은 되돌릴 수 없습니다.

그렇다고 AI 사용을 막을 수는 없습니다. 그래서 저희는 막는 대신 **보내기 전에 거르는 문**을 하나 만들었습니다.

## 2. 누가 쓰는가 (1분)

사용하는 사람은 세 부류입니다.

첫째, **웹에서 ChatGPT나 Claude를 쓰는 직원**입니다. 크롬 확장 하나만 깔면 됩니다. 평소처럼 쓰면 확장이 글을 보내기 직전에 검사합니다.

둘째, **사내 앱이나 AI 에이전트를 만드는 개발자**입니다. 저희 서버는 OpenAI와 같은 형식의 주소를 열어 둡니다. 그래서 코드에서 주소 하나만 바꾸면, 앱이 보내는 모든 요청이 같은 검사를 거칩니다. 도구를 쓰는 에이전트도 지원합니다.

셋째, **보안 담당자와 관리자**입니다. 웹 콘솔에서 규칙을 만들고, 예외 요청을 승인하고, 무엇이 몇 건 걸렸는지 기록을 봅니다.

대상 회사는 지켜야 할 정보가 뚜렷한 곳입니다. 화장품, 금융, 의료, 제조, IT처럼 업종마다 새면 안 되는 정보가 다릅니다.

## 3. 전체 구조 (1분 30초)

`[구조도 슬라이드]`

입구는 앞서 말한 둘입니다. 확장과 사내 앱입니다. 둘 다 같은 **게이트웨이**로 들어옵니다. 게이트웨이는 FastAPI로 만든 서버 하나입니다.

게이트웨이 안에서는 글이 이 순서로 처리됩니다.

1. **탐지**: 글에서 민감정보를 찾습니다.
2. **판정**: 찾은 것마다 가릴지, 막을지, 기록만 할지 정합니다.
3. **가림**: 값을 `[사람_1]` 같은 이름표로 바꿉니다.
4. **전송**: 가려진 글만 외부 모델로 나갑니다.
5. **답변 검사와 복원**: 돌아온 답변도 한 번 검사하고, 이름표를 원래 값으로 되돌려 보여 줍니다.

여기서 중요한 점은 원본이 어디에 있느냐입니다. 원본 값은 요청 동안만 서버 메모리의 임시 금고에 있고, 그 요청이 끝나면 사라집니다. 서버에 원문을 저장하지 않습니다. 기록에는 무엇이 몇 건 걸렸는지, 누가 어느 사이트에서 보냈는지만 남습니다.

서버는 콘솔 화면까지 한 번에 내놓는 하나의 서비스입니다. Docker로 묶어 Railway에 올렸고, 코드를 합치기 전에 자동 시험 네 종류가 돌아갑니다.

## 4. 핵심 방식, 그리고 지금 실제로 되는 것 (2분 30초)

**먼저 설계 의도입니다.**

모델에게 "[가려짐]"이라고만 보내면 아무 일도 시킬 수 없습니다. 그래서 저희는 **종류가 보이는 이름표**로 바꾸려고 했습니다. "고객 홍길동에게 사과 메일을 써 줘"는 모델에게 "고객 [사람_1]에게 사과 메일을 써 줘"로 갑니다. 모델은 이게 사람 이름이라는 것을 알고 메일을 쓰고, 실제 이름은 모릅니다. 답변이 돌아오면 `[사람_1]`을 홍길동으로 되돌립니다.

이 방식은 Presidio 같은 오픈소스 PII 가림 도구가 쓰는 방식과 같습니다. 저희는 그 도구를 가져다 쓴 것이 아니라, **같은 방식을 한국어와 업종에 맞춰 직접 구현했습니다.**

**여기까지가 저희가 만들려던 것이고, 지금 실제로 어디까지 되는지도 그대로 말씀드리겠습니다.**

- **서버는 이 구조가 끝나 있습니다.** 가리기, 이름표 만들기, 답변 복원이 모두 동작하고 자동 시험 275개로 확인했습니다.
- **크롬 확장은 실제 ChatGPT 화면에서 돌려 봤습니다.** 보내기 전에 글을 가리고, 답변에서는 원래 값으로 되돌려 보여 줍니다. 다만 한계가 세 가지 있습니다.
  - 복원에 쓰는 원본은 서버 메모리에 30분만 둡니다. 탭을 새로 열거나 30분이 지나면 이름표가 그대로 보입니다.
  - ChatGPT가 따로 그리는 메일 카드 같은 일부 영역에서는 이름표가 복원되지 않고 남을 수 있습니다.
  - 모델이 이름표를 빈칸으로 오해해서 "받는 분이 누구인가요?" 하고 되묻는 경우가 있어서, 글 끝에 "이건 가려 둔 자리표시자니 그대로 쓰세요"라는 안내 문구를 덧붙여 보냅니다.
  - **Gmail처럼 ChatGPT가 대신 실행하는 외부 도구는 이름표를 되돌리지 못합니다.** 예를 들어 이메일 주소를 말하고 "초안 써서 연결된 Gmail로 보내 줘"라고 하면 초안까지는 되지만, 발송은 주소가 `[이메일_1]`인 채로 전달돼서 실패합니다. 이 통신은 OpenAI 서버가 Google 서버를 직접 부르는 일이라 브라우저 확장이 끼어들 수 없습니다. 이런 경우에는 모델을 게이트웨이 서버를 거쳐 부르게 해야 하고, 그 경로는 서버에 구현해 가짜 모델로 시험까지 마쳤습니다.
- **관리자 화면에는 아직 없는 부분이 있습니다.** 규칙을 시험해 보는 화면은 있지만, 글이 이름표로 바뀌고 모델을 거쳐 복원되기까지의 전 과정을 한 화면에서 보여 주는 기능은 아직 없습니다.
- **사내 앱용 API는 아직 가짜 모델로만 시험했습니다.** 실제 모델 연결은 키를 넣은 뒤에 확인할 예정입니다.

**정리하겠습니다.** 가리고 복원하는 핵심 구조는 서버에서 완성했고, 화면 쪽 마감과 실제 모델 연결 확인이 남았습니다. 이것이 오늘 기준의 실제 상태입니다.

> 여기까지 발표하고 마무리합니다. 5~8번은 참고용입니다.

## 5. 저희만의 차이: 업종 템플릿 (1분 30초)

범용 도구는 이름, 주민번호, 전화번호 같은 흔한 개인정보만 잡습니다. 그런데 회사에 정말 중요한 정보는 업종마다 다릅니다. 화장품 회사에는 조성비가, 금융에는 계좌번호가, 법무에는 사건번호가, 물류에는 컨테이너 번호가 그렇습니다.

그래서 탐지를 세 겹으로 쌓았습니다.

- **기본 규칙**: 주민번호, 전화번호의 여러 표기, 이메일, 사업자번호, IP 등 17개입니다. 숫자 범위와 날짜까지 검증해서 오탐을 줄였습니다.
- **시크릿 탐지**: 오픈소스 gitleaks의 규칙 222개를 가져와 변환해서 씁니다. API 키, 토큰, 개인키, DB 접속 주소를 막습니다. 검증된 규칙이 있는데 다시 만들 이유가 없었습니다.
- **업종 템플릿**: 9개 업종, 41개 항목을 YAML 파일로 만들었습니다. 코드를 고치지 않고도 새 업종이나 항목을 추가할 수 있습니다.

`[비교표 슬라이드]`

효과는 수치로 확인했습니다. 업종 항목을 기준으로, 범용 규칙만으로는 약 **4%** 가 잡혔고 업종 템플릿을 더하면 **100%** 가 잡혔습니다. 범용 도구가 그냥 통과시키는 조성비를 저희는 영업기밀로 가립니다. 이것이 저희의 차별점입니다.

여기에 회사가 직접 규칙을 만드는 정책 엔진이 있습니다. 콘솔에서 만든 규칙은 초안, 적용, 버전으로 관리하고 문제가 생기면 이전 버전으로 되돌립니다.

## 6. 막기만 하지 않는다: 예외와 기록 (1분 10초)

`[채팅 화면과 콘솔 화면을 번갈아 시연]`

모든 것을 막으면 일이 안 됩니다. 그래서 예외 요청이 있습니다. 직원이 막힌 화면에서 이유를 적어 요청하면, 관리자가 콘솔에서 1회 또는 시간을 정해 승인합니다. 승인된 항목은 정해진 시간 동안, 요청한 사이트에서만 실제로 통과합니다. 직원의 채팅 화면에는 승인 사실과 남은 시간이 나오고, 1회 승인은 쓰는 즉시 끝납니다. 안 쓴 승인은 하루 뒤에 사라지고, 관리자는 언제든 회수할 수 있습니다. 예외로 나간 글은 기록에 따로 표시됩니다.

## 7. 왜 LLM 없이 규칙으로 했는가 (50초)

탐지에 또 다른 LLM을 쓰지 않은 것은 의도한 선택입니다. 민감정보를 찾으려고 그 정보를 다른 AI에 넘기면 앞뒤가 맞지 않습니다. 규칙 기반은 같은 입력에 항상 같은 결과가 나오고, 어떤 규칙 때문에 걸렸는지 설명할 수 있고, 별도 모델 서버가 필요 없고, 빠릅니다.

한계도 있습니다. 숫자만 적힌 계좌번호처럼 문맥이 있어야 구분되는 정보는 앞뒤 키워드가 있어야 잡습니다. 이 부분은 로컬 LLM으로 보완할 수 있게 구조를 열어 두었고, 다음 단계로 둡니다.

## 8. 마무리 (30초)

정리하면, 직원은 평소대로 AI를 쓰고, 개발자는 주소만 바꾸고, 보안 담당자는 한곳에서 규칙과 예외와 기록을 봅니다. 가려진 글만 밖으로 나가고, 원본은 서버에 남지 않습니다. 시험 275개와 이상 입력 시험으로 서버가 멈추지 않는 것도 확인했습니다. 다음 단계는 사내 계정 연동과 문맥 판단 보강입니다.

## 예상 질문

- **LLM이 더 잘 잡지 않나요?** 문맥 판단은 LLM이 낫습니다. 하지만 그러려면 원문을 또 다른 모델에 보내야 하고 비용과 지연이 생깁니다. 규칙을 먼저 두고 모호한 것만 LLM으로 보완하는 구조를 다음 단계로 잡았습니다.
- **규칙을 피해 가면요?** 정규식의 한계입니다. 그래서 회사가 규칙을 계속 추가하는 정책 엔진을 두었고, 놓친 사례를 규칙으로 되돌리는 운영을 전제로 합니다.
- **원문은 어디에 저장되나요?** 저장하지 않습니다. 요청 동안만 서버 메모리의 금고에 있고, 기록에는 무엇이 몇 건 걸렸는지만 남습니다.
- **로그인은요?** 지금은 브라우저 번호와 앱 키로 구분합니다. 사내 계정 연동은 다음 단계입니다.
- **Presidio를 쓴 건가요?** 아닙니다. 같은 방식을 직접 구현했고, 시크릿 규칙만 gitleaks를 가져다 썼습니다.
