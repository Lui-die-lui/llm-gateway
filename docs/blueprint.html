사내 민감정보를 외부 LLM 밖으로 내보내지 않는 게이트웨이

직원과 사내 앱이 ChatGPT 같은 외부 LLM을 쓸 때, 요청이 회사 밖으로 나가기 직전 게이트웨이가 가로채 민감정보를 가립니다. 핵심은 가렸다가 되돌리기(redact → restore) — 외부 모델에는 가린 채 보내고, 응답이 오면 내부에서 원래 값으로 복원합니다.

01

02

데이터 흐름 (왕복)

요청은 나갈 때 가려지고, 응답은 돌아올 때 복원됩니다. 양방향 모두 검사하는 것이 포인트 — 외부 모델이 실수로 민감정보를 되뱉거나, 프롬프트 인젝션으로 유출을 시도하는 경우도 응답 경로에서 잡습니다.

요청 경로 → 내부에서 외부로

  1. 요청 수신

    사내 앱이 게이트웨이의 OpenAI 호환 엔드포인트로 호출. 앱 입장에선 평소와 동일.

  2. 민감정보 탐지

    규칙(정규식) + NER + 산업 taxonomy로 PII·시크릿·영업기밀을 식별.

  3. 정책 판정

    항목별로 redact / block / internal_only 결정.

  4. 토큰 치환

    민감값을 [유형_n] 자리표시자로 교체.매핑은 내부 볼트에만 저장

  5. 외부 전송

    정제된 프롬프트만 외부 LLM으로 전달.

← 응답 경로 외부에서 내부로

  1. 응답 수신

    외부 LLM의 답변을 게이트웨이가 받음(스트리밍 포함).

  2. 응답 스캔

    답변에 새로운 민감정보가 섞였는지 역방향 검사.

  3. 토큰 복원

    볼트의 매핑을 참조해 [사람_1]을 다시 홍길동으로 복원.

  4. 직원에게 전달

    복원된 완전한 답변을 사내 앱으로 반환.

  5. 감사 기록

    내용이 아닌 메타데이터(유형·건수·정책·시각)만 로그에 남김.

04

차별점 — 산업별 민감정보 taxonomy

기존 오픈소스 게이트웨이는 전부 "PII 일반론"입니다. 이름·주민번호는 잡아도 "그 산업에서 진짜 중요한 데이터"는 모릅니다. 산업을 통째로 템플릿화하면 폭발하므로, 3개 축으로 분해해 조합으로 재사용합니다.

축 1 · WHAT

데이터 유형

그 산업에서 민감한 데이터가 무엇인가.

진단명 · 처방조성비 · 공급처도면 치수계좌 · 신용등급
축 2 · WHERE

활용처

LLM을 어디에 쓰는가. 쓰임마다 흐르는 데이터가 다름.

고객상담문서요약코드생성번역
축 3 · HOW

데이터 흐름

어디서 와서 어디로 가는가.

내부DB→LLM→직원고객입력→LLM→외부저장
조합이 핵심. "고객상담" 활용처 템플릿은 병원이든 쇼핑몰이든 공통으로 쓰고, 거기에 산업별 "데이터 유형"만 끼웁니다. 그래서 산업이 늘어도 템플릿 수가 폭발하지 않고, 새 산업 진출 = 템플릿 한 벌 추가로 확장됩니다. 이것이 "컨설팅"이 아니라 "플랫폼"인 이유입니다.
05

Taxonomy 스키마

정규화된 이 템플릿 묶음이 제품의 핵심 지식자산입니다. 스키마만 확정하면 팀원들이 산업별로 병렬 작성에 들어갈 수 있습니다. 캡스톤에선 2개 산업만 채웁니다 — 하나는 팀 내 실무 지식이 있는 화장품/규제 도메인.

industries/cosmetics.yaml
industry: cosmetics
entities:
  - id: formulation_ratio        # 조성비 (영업기밀)
    detection:
      patterns: ['\d+(\.\d+)?\s*%']     # 1차: 정규식 힌트
      context_keywords: ['조성', '배합', 'INCI', '함량']
      ner_hint: "화장품 원료 배합 비율"   # LLM 판정용
    sensitivity: critical
    action: redact                  # redact / block / internal_only
    regulation: ['영업비밀보호법', 'CPNP']

  - id: supplier_source           # 원료 공급처
    detection:
      context_keywords: ['공급사', '원료처', '제조원']
      ner_hint: "원료 공급업체명"
    sensitivity: high
    action: internal_only           # 내부 모델로만 라우팅

applies_to:                        # 축2·축3 조합
  use_cases: [document_summary, translation]
  flow: internal_db_to_llm
id민감정보 유형 식별자 (축1: 데이터 유형)
detection정규식 + 문맥 키워드 + NER 힌트의 다층 탐지 신호
sensitivity민감도 등급 (critical / high / medium)
action처리 정책 (가림 / 차단 / 내부라우팅)
regulation연관 규제 — 감사·증빙에 매핑
applies_to활용처·흐름 조건 (축2·축3) — 정책을 조건부로 조정
06

전부 오픈소스·자체호스팅. 탐지 보조 LLM도 로컬(Ollama)로 돌려 "탐지조차 외부로 안 나간다"를 셀링포인트로 만듭니다. 단, 데모 안정성은 규칙 기반이 받칩니다.

7일 개발 계획

원칙은 "걷는 뼈대부터". Day 1에 전원이 같은 최소 파이프를 돌려본 뒤 갈라집니다. 각자 멋진 부분을 따로 만들다 마지막 날 안 합쳐지는 게 1주 프로젝트가 망하는 1순위 이유입니다.

Day 1전원 공동

걷는 뼈대 — 끝까지 작동하는 최소 파이프

FastAPI OpenAI 호환 프록시 + Presidio 기본 탐지 하나. "이메일 든 프롬프트 → [EMAIL]로 가려져 나간다"까지만. 산업 템플릿은 아직 없음. 이게 되면 프로젝트는 이미 60% 성공.

선택한 산업 템플릿이 탐지 엔진에 자동 적용되고, 로컬 LLM 탐지 보조를 얹습니다. 응답 스캐너·감사 로그 연동.

통합 · 측정 · 리허설

범용 Presidio vs 산업 템플릿 탐지율 비교표(= 발표의 무기)를 완성하고, 라이브 데모를 녹화본과 함께 준비. "템플릿을 산업별로 복제하면 플랫폼이 된다"는 확장 슬라이드 1장.

"성공"의 한 문장

범용 Presidio는 통과시키는 조성비를, 우리 템플릿은 영업기밀로 잡아 가린다 — 이 before/after 한 장면을 라이브로 보여주면 데모는 성공. 모든 작업의 기준선으로 삼으세요.

08

리스크 & 범위

일주일 안에 완전한 셀프서비스 플랫폼은 불가능합니다. 무엇을 안 할지 먼저 못 박는 것이 무엇을 할지 정하는 것만큼 중요합니다.

리스크 · 안전장치

  • 탐지 오류 — LLM 판정은 틀릴 수 있다. "AI 제안 → 사람 1회 확인" 검증 레이어를 넣고, 발표에서도 "100% 자동이 아니라 전문가 1명이 여러 명 몫"이라고 솔직하게.
  • 볼트 유출 — 치환 매핑이 새면 가림이 무의미. 매핑은 요청 세션 스코프로만 두고 외부 경로·로그에 절대 남기지 않는다.
  • 데모 불안정 — 로컬 LLM이 데모 날 느려질 수 있다. 로컬은 탐지 보조로만, 데모 안정성은 규칙 기반이 받친다. 라이브는 녹화본 백업 필수.

이번 주 범위 밖 (의도적 제외)

  • 브라우저 ChatGPT 차단 — 네트워크 레벨 통제라 1주엔 무리. 대상은 "사내 앱 → LLM API"로 고정.
  • 하이브리드 라우팅 완성 — 우선 "가려서 외부로"(방향 1)만. 내부 모델 라우팅은 되면 추가.
  • 산업 3개 이상 — 2개(화장품·의료)로 고정. 3개째 넣고 싶으면 그 시간에 발표를 다듬는 게 이득.
  • 셀프서비스 온보딩 — 자동 가입·결제는 발표 슬라이드의 확장 시나리오로만.
